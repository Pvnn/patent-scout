# Skill: Report Drafter

## When to Use
Use this skill at **Step 4** of the analysis pipeline. It synthesizes the outputs of the previous 3 steps into a final, client-ready markdown report. This agent streams its output token-by-token directly to the frontend.

## Contract Rules
1. **Fixed Structure**: The report MUST adhere to the 4 fixed sections listed below. Do not invent new sections.
2. **Professional Tone**: Language must be objective, legal-adjacent, and analytical. Avoid informal phrasing.
3. **No External Tools**: This is the only agent that does not spawn a heavy subprocess for data retrieval; it processes the state passed from Step 3 and uses an LLM to format the Markdown.

## Expected Markdown Structure
The output must be formatted exactly as follows:

```markdown
## Prior-Art Analysis: [Title]

### 1. Executive Summary
[One paragraph summarizing overall risk level and number of concerning patents]

### 2. Risk Assessment
| Patent No. | Title | Score | Confidence | Risk Level |
|------------|-------|-------|------------|------------|
| [No.]      | [...] | [...] | [...]      | [HIGH]     |

### 3. Claim-by-Claim Analysis
**Patent: [Patent No.]**
* **User Claim:** [Text]
* **Patent Claim:** "[Verbatim Quote]"
* **Analysis:** [Why they overlap based on Step 3 reasoning]

### 4. Recommended Next Steps
1. [Actionable guidance, e.g., FTO opinion]
2. [Actionable guidance, e.g., design-around]
```

## Tool Call Format
While the LLM handles the streaming natively, to trigger the final save, use:
`run_tool("report_drafter", {"markdown_content": "<full string>", "session_id": "..."})`

## Anti-Patterns
* **Altering Scores**: Do not change the `similarity_score` or `risk` levels generated by Step 3. Your job is to report, not re-evaluate.
* **Deviating from Markdown**: Do not use HTML tables or plain text formats. Strict GitHub-flavored markdown is required.
